# 技术可行性与实现路径分析（2026-11-10）

> 面向新要求：游戏引擎（Unity / Unreal）＋高斯泼溅（3DGS）＋「逐个建筑与景观建模，最后合成到整张地图」。
> 结论先行：**引擎换成 Unity/Unreal 在本机不可行且会破坏"单文件可玩"的交付要求；3DGS 用现有素材无法重建**。
> 推荐路径：**引擎无关的资产管线（逐栋 GLB）＋ three.js 主场景合成**；3DGS 作为可选的"写实图层"仅在用户提供环绕视频后启用。
> 本文所有数字都在本机实测或按官方规格核算，可复核。

## 二、四种引擎/运行时的可行性对比

| 方案 | 安装成本 | 本机可跑 | 产物形态 | 对"单个 HTML 双击运行"的兼容 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **three.js（现状）** | 0（已内联） | ✅ 已验证 60 FPS 级 | 单 HTML 1.65 MB | ✅ 完全兼容 | **保留为运行时** |
| Unity 6 + WebGL | ~20 GB + 许可证 | 可能（8 GB 显存够） | 构建目录（wasm+data，30–80 MB），**不能塞进单 HTML** | ❌ 需 HTTP 服务，file:// 直接被浏览器拦 | 只作**可选**导出目标 |
| Unreal Engine 5 | ~70 GB + DDC | 勉强（显存/磁盘吃紧） | Windows 包（数百 MB）；网页只能 Pixel Streaming（需服务器 GPU） | ❌ 完全冲突 | **不建议** |
| Godot 4 | ~200 MB，MIT | ✅ 轻量 | Web 导出（wasm，10–30 MB），仍需服务器 | ⚠️ 近似 Unity 的限制 | 不必要（不如直接 three.js） |

**关键判断**：把运行时换成 Unity/Unreal，会同时损失"单文件、双击即开、零安装"三项已交付能力，而画面提升主要来自**资产质量**而非引擎。因此**先提升资产（逐栋建模），再决定运行时**——资产是引擎无关的，这是唯一不返工的顺序。

## 三、3DGS（高斯泼溅）可行性分析 —— 结论：现有素材无法重建

### 3.1 技术前提（硬性）
3DGS / NeRF / 摄影测量都要求**同一物体、密集、有重叠、位姿可解算**的多视角影像：
- 每个物体 **80–300 张**（或 1–3 分钟环绕视频，抽帧 150–600 张），重叠率 > 60%；
- 相机内参一致、光照尽量稳定、无运动物体、无遮挡跳变；
- 需要 COLMAP 做 SfM 求位姿（每栋 5–30 分钟）；再训练 10–40 分钟（RTX 5060，小场景）。

### 3.2 我们手上的素材
| 来源 | 数量 | 是否可解算 |
| --- | --- | --- |
| 用户实拍（中原楼 3 张、图书馆 2 张） | 5 | ❌ 视角不重叠、不同时间/设备 |
| 百度地图 POI 相册（15 栋 × 2–5 张） | ~50 | ❌ 跨来源、跨时段、带水印、广角畸变不明 |
| 抖音 AI 生成视频截帧（12 张） | 12 | ❌ **生成内容，不是真实几何** |

**结论：现有素材做不出可用的 3DGS 模型。** 强行训练只会得到糊团 + 错误几何，属于"错上加错"，明确不做。

### 3.3 如果要做，需要你提供的采集规范（每栋 1–3 分钟）
- 手机/相机 4K 30fps，**围绕建筑走一圈**（或半圈 180° + 正立面平移），保持画面重叠 ≥ 60%；
- 距离 = 楼高的 0.8–1.5 倍；不要变焦；尽量顺光、避免行人车辆穿画面；
- 每栋单独一段视频，文件名 = 楼名；同一栋不要混剪不同日期。
- 交付后可得到：`.ply/.splat`（写实但**无碰撞**、无昼夜变化、单栋 50–300 MB）。
  → 网页端用 splat 渲染器可 30–60 FPS；但要走动就必须另做碰撞代理，且体积与"单文件"冲突，**只适合 2–3 个明星地标**。

### 3.4 更适合"游戏化校园"的替代：摄影测量网格（Meshroom/RealityCapture）
同样需要多视角视频，但产出**带纹理的可碰撞网格**（20–80 万面/栋），可直接进游戏引擎、可做 LOD、可烘焙光照。若你愿意拍视频，**优先做摄影测量而不是 3DGS**。

## 四、推荐实现路径（不返工的分阶段方案）

### 阶段 0：资产盘点与废弃决策（本轮已做）
- **保留**：真实布局数据（`src/world/layout.js`，百度 POI 换算，192 个校内点）、道路/水系/地形、交互与物理（探针全绿）、UI/地图。
- **重建**：所有"程序化盒子 + 通用窗格贴图"的楼栋几何。它们不是"错在位置"，而是**错在形制**——用一张通用立面贴图套 70 栋楼，再修也修不出辨识度。按你的指示"搭错的及时舍弃"，逐栋以照片为准重写，不做局部打补丁。
- **废弃**：AI 生成视频截帧作为几何依据（仅保留为配色/氛围参考）。

### 阶段 1：逐栋资产化（核心工作，引擎无关）
每栋楼产出一个**独立资产**：
```
assets/buildings/<楼名>.glb      # 几何 + PBR 材质 + 楼层/窗带结构 + 楼名贴片
assets/buildings/<楼名>.json     # 包围盒 / 碰撞代理 / LOD / 锚点（入口、台阶、雨棚）
assets/buildings/<楼名>_tex/*.png# 由照片裁切/矫正得到的立面贴图（可选）
```
- **几何来源**：参数化建模器（按"层数 × 开间 × 进深 × 屋顶形制 × 入口形制"生成），参数来自照片量测；
- **贴图来源**：从 POI 相册照片中裁切正立面，做透视矫正 → 去水印 → 无缝化，作为该楼的专属立面贴图（这是"像"的关键，成本低、收益大）；
- **验收标准**：在 60 m 距离、人眼高度看该楼，能仅凭轮廓 + 立面辨认出是哪一栋（对着照片比对）。
- **产出格式**：glTF 2.0 二进制（`.glb`）。Unity / Unreal / three.js 三方都能直接导入——**这是"不返工"的关键**。

### 阶段 2：主场景合成
- 用 `layout.js` 的真实坐标把 GLB 摆回地图（已有坐标体系，不需重算）；
- 地形、道路、水系、围墙、树木、街具继续由现有系统生成（已验证性能：487 draw calls / 945k tris）；
- 逐栋替换：**每替换一栋就截图对比，确认无回归再替换下一栋**。

### 阶段 3（可选）：运行时升级
- 若最终仍要"单文件 HTML"：把 GLB 以 base64 内嵌（单栋 200–600 KB，70 栋约 20–40 MB，可接受）；
- 若你更看重画质、可接受"文件夹 + 本地服务器"：同一批 GLB 直接导入 Unity 6 做 WebGL 构建，**无需重做资产**。

## 五、逐栋建模的工序（每栋 30–60 分钟，可并行 2 路）

1. **照片整备**：裁正立面、透视矫正、量测层数/开间/层高比、取主色与玻璃色（输出 `spec.json`）。
2. **体量**：按层高 × 层数生成主体，裙房/塔楼/退台分开；确认檐口高度与 `layout.js` 的 h 一致（±10%）。
3. **立面**：窗带 / 幕墙 / 拱窗 / 壁柱 / 遮阳板，按照片节奏排布；贴图用该楼专属立面。
4. **屋顶**：平顶女儿墙 / 四坡瓦 / 攒尖 / 筒拱 / 网架，按照片。
5. **入口**：台阶、雨棚、门厅、坡道、楼名（金字/石牌）。
6. **细节**：空调外机、雨水管、屋顶设备、旗杆、连廊接口。
7. **碰撞与 LOD**：AABB 或凸包碰撞；LOD1（≤300 面）用于 300 m 外。
8. **验收**：三机位截图（正立面 / 45° / 远景）与照片并排比对，写进 `work/polish-log.md`。

## 六、风险与对策

| 风险 | 对策 |
| --- | --- |
| 70 栋 × 逐栋精修 = 工作量巨大 | 分优先级：先 12 栋"上镜"的（图书馆/中原楼/文泰/文澜/文波/文泉/会堂/体育馆/体育中心/四门/钟楼）；宿舍/食堂用"同型批量 + 差异贴图" |
| 照片角度不全，背面/侧面无依据 | 用"已知面推未知面"（同型楼类比），并在 `polish-log` 标注"推断" |
| 内嵌 GLB 后单文件过大 | 只内嵌主力 30 栋，其余按需；或提供"素材包 + HTML"双形态 |
| 3DGS 数据不达标 | 不训练；等合规采集。宁缺毋滥 |
| 并发导致机器卡死 | 同一时刻只跑 1 个渲染/导出任务，截图串行（已验证 5 s/张） |

## 七、需要你决策/提供的

1. **运行时**：确认「保留 three.js 单文件」还是「Unity WebGL 文件夹」——前者保住交付形态，后者要多装 ~20 GB。资产通用，晚决定也不返工。
2. **3DGS**：是否愿意为 2–3 个明星地标拍环绕视频（每栋 1–3 分钟，规范见 §3.3）。不拍则本轮不做 3DGS。
3. **照片补齐**（当前缺口）：文澜楼、钟楼、五羊广场雕塑、国际学术交流中心、希贤岭；以及任意楼的**侧面/背面**（现有相册以正立面为主）。
4. 是否接受"文件夹形态"（HTML + assets/），若接受可显著提高贴图分辨率与楼栋数量。
